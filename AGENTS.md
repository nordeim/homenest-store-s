# AGENTS.md — HomeNest Kitchen

Production e-commerce storefront + admin console: Next.js 16 (App Router) · React 19 · TypeScript strict · Tailwind CSS 4 (CSS-first) · Prisma 6 + SQLite · Radix/shadcn-style UI · Vitest + Playwright. A visual-and-functional superset clone of `https://nest-culinary-hub.base44.app/`.

## Environment shadowing (sandbox trap)

Any `DATABASE_URL` already present in the process environment (shell export, CI inject, parent `.env`) **wins over the repo `.env`** — Prisma never overrides existing process env. Symptom: `db/custom.db` never appears at the repo root, or rows survive "fresh" reseeds (the file being written is elsewhere). Diagnose with `node -e "console.log(process.env.DATABASE_URL)"` from the repo root. If the shadowed path differs, converge them (symlink) or unset before running DB commands.

## DATABASE_URL contract (pinned by tests/unit/db-path.test.ts)

`.env` carries `DATABASE_URL="file:../db/custom.db"`; `db/` lives at the repo root (git-ignored). A **relative** `file:` URL resolves against `prisma/schema.prisma` — for the CLI AND at runtime via `src/lib/db-path.ts` — so `db:push`, `db:seed`, `next dev`, `next build` and the standalone server all open ONE file at `<repo>/db/custom.db` regardless of CWD. Absolute `file:` URLs and non-SQLite URLs pass through untouched. If you move the schema or the db folder, update that test first.

## Tailwind v4 trap log (violating these breaks production renders)

1. **Never JS-toggle a display utility.** v4 changed display-utility generation order, so toggling the `hidden` class on an element that also carries `flex`/`block` is unreliable (tailwindlabs/tailwindcss#15884, #18653; preflight's `[hidden]` is `!important`). Overlays/menus mount conditionally via React state or use transform/opacity. Pinned by `tests/e2e/mobile-navigation.spec.ts`.
2. **Theme colors are FULL `hsl()` values** in `@theme inline` — bare `H S% L%` triplets silently resolve to transparent.
3. **`hover:` is un-gated**: `@custom-variant hover (&:hover)` in `globals.css` restores v3 semantics so touch devices still render hover styles.
4. **`--shadow-sm` is pinned to v3 geometry**; the radius scale is pinned to the reference's measured px. Don't "upgrade" these pins.
5. Config is CSS-first (`@theme` in `src/app/globals.css`) — there is no `tailwind.config.js` and none should be added.
6. `reactStrictMode: false` in `next.config.ts` is deliberate: StrictMode's dev double-invocation produces double `useEffect` fetches in the cart-drawer/cart-summary islands that race the per-line pending locks. Re-enable only together with a re-audit of every fetch effect.
7. The hero carousel pauses auto-rotation on hover/focus and under `prefers-reduced-motion` (WCAG 2.2.2) via `useSyncExternalStore` — do NOT replace that with a set-state-in-effect `matchMedia` listener (lint's `react-hooks/set-state-in-effect` rejects it, correctly).

## CSP nonce trap (Next 16 + `src/proxy.ts`)

The proxy stamps a **per-request nonce** CSP on every response; Next applies the request-header nonce to the scripts it renders. A **prerendered/static page bakes no (or build-time) nonces** → the browser silently refuses its scripts → hydration never happens, with zero console errors. Symptom: a page that loads, paints, but never hydrates. Fix: make the route render per-request (`await connection()` in the layout — `force-dynamic` alone did NOT de-prerender in Next 16.4). The `(auth)` layout carries this fix with a comment; don't remove it. Pinned by the auth e2e specs.

## Architecture invariants

- **RSC by default**; `"use client"` only for interactive islands. Server Actions (`src/lib/actions/*.ts`) for form mutations; REST route handlers (`src/app/api/*`) for client-island fetches (cart, wishlist, checkout, coupon, contact, addresses, search, newsletter, health).
- **Money is INTEGER CENTS everywhere.** Format with `formatMoney` (`src/lib/money.ts`), parse input with `parseDollarsToCents`. Checkout totals are re-derived server-side via `computeOrderMoney` (`src/lib/order-money.ts`) — client totals are display mirrors only. `tests/unit/order-money.test.ts` pins the math.
- **Zod at the boundary**: every external input (FormData, JSON body) is parsed by `src/lib/validation.ts` schemas before it touches Prisma. SQLite has no enums; status/role vocabularies live there.
- **Cart/wishlist are DB-backed with guest token cookies** (`homenest_cart`, `homenest_wishlist`); on login the guest cart merges into the user's. Sessions are DB rows with HMAC-signed `homenest_session` cookie (`src/lib/auth.ts`); passwords are scrypt (`src/lib/password.ts`).
- **Admin surface is role-gated server-side**: layouts/actions check `getCurrentUser().role === "admin"`; client checks are UX only, never the gate.
- **Toast context wraps children** in the root layout (`<Toaster>{children}</Toaster>`) — it must be an ancestor of every page, not a sibling.
- Mobile menu contract: push-down panel (reference-matched), conditionally mounted, never `hidden`-toggled; green circular close button; active link = `bg-primary` pill.
- **Order tracking is access-controlled**: `/track-order` requires the order number **plus the purchase email** (`trackOrderSchema` + `emailsMatch` in `src/lib/order-tracking.ts`); wrong-email/missing-email/unknown-number render the same alert. Pinned by the shopping-flow e2e spec. Never loosen this back to number-only.
- **The checkout receipt is token-gated AND every idempotency path is ownership-bound**: `/api/checkout` returns `{ orderNumber, token }` (`src/lib/order-access.ts`, HMAC of the number keyed by `AUTH_SECRET`); `/checkout/success` renders the full receipt **only** for a valid `order`+`token` pair. `replayAuthorized` gates the pre-tx replay AND — since session-7 S7-2 — the P2002 recovery path in `placeOrderWithRetry` routes through `resolveReplay` (same rule: user replays for the same session, guest replays with the same cart-token cookie, legacy rows deny → 409). A leaked key alone reveals nothing. The page is `noindex`. Never render PII from a bare `?order=` param again.
- **Checkout is idempotent AND ownership-bound**: the client generates `crypto.randomUUID()` once per checkout visit and sends it as `idempotencyKey`; a replay (same key) returns the already-placed order's receipt instead of double-ordering. `Order.idempotencyKey` is a nullable unique column; a `P2002` on it resolves to the winning order (the retry loop only retries `number` collisions). A replay is additionally bound to the placing client (session-6 S6-8): user orders replay only for the same session, guest orders only with the same cart-token cookie (`Order.cartToken`, `replayAuthorized` in `src/lib/order-access.ts`, unit-pinned) — a leaked key alone reveals nothing.
- **Money is derived inside the checkout transaction**: subtotal comes from the in-tx product snapshots (never the pre-tx cart summary), the coupon is re-validated and its `timesUsed` incremented inside the tx, and `computeOrderMoney` runs there. The pre-tx coupon check is a fast-fail UX path only.
- **Cancelled orders restock exactly once — and the transition write is its own guard** (session-9 S9-2): `setOrderStatusAction` re-reads the order INSIDE the `$transaction` and routes through `applyOrderStatusTransition` (`src/lib/order-status.ts`), whose conditional `updateMany({ where: { id, status: <in-tx status> } })` only lands when the order is still in the state just read — two admins who both read `pending` and submit `cancelled` can no longer BOTH restock, and a stale submission can never reopen a terminal order (count === 0 → typed conflict → the accurate transition error). `canTransitionOrderStatus`/`shouldRestockOnStatusChange` keep the workflow rules; the pre-tx read is a fast-fail UX check only.
- **The header cart badge falls back to the server-computed count** (session-9 S9-1): the store context's `cartCount` is `number | null`, initialized `null` on server AND client — StoreChrome's `liveCount ?? cartCount` renders the per-request server prop on every fresh load, and only in-page mutations take over. Initializing at 0 made that fallback dead code (a shopper with items saw a badge-less cart on every hard load). The storefront layout's `findCartId`+`getCartSummary` feed this prop — do not "optimize" them away.
- **Address default promotion is race-safe** (session-9 S9-3): PATCH `/api/addresses` promotes FIRST via the scoped conditional `updateMany` inside `promoteAddressInTx` (`src/lib/addresses.ts`) and only then unsets the others, inside ONE `$transaction` — a concurrent delete aborts with `AddressGoneError` → 404 and the previous defaults are never stranded; DELETE uses a scoped `deleteMany` with `count === 0` → 404 (the S8-4 wishlist pattern — P2025 can never surface as a 500). **Deleting the DEFAULT address re-promotes the newest remaining row in the SAME transaction** (session-10 S10-1, `reassignDefaultAfterDeleteInTx`) — the book can never strand at zero defaults, so checkout prefill survives every delete.
- **Login merges the guest cart + wishlist, and the first login CLAIMS it**: `loginAction`/`registerAction` call `getOrCreateCart`/`getOrCreateWishlist` after `createSession` (best-effort). Don't remove — without it a guest with a full cart sees a stale cart after signing in. Session-7 S7-1: when the user has NO own cart, the token-unique P2002 winner is the guest row — `safeCreateCart`/`safeCreateWishlist` claim it with a guarded `updateMany({ where: { id, userId: null } })` (never steals a claimed row; a lost claim self-heals via the merge branch). Pinned by the auth e2e cross-device case.
- **Coupons have a lifecycle**: `isCouponRedeemable` (`src/lib/coupons.ts`) gates on `isActive`, `expiresAt`, and `maxRedemptions`/`timesUsed` at lookup AND inside the checkout tx; the in-tx `timesUsed` increment is an **atomic guarded `updateMany`** (`couponRedemptionWhere` — `count === 0` rolls the order back with a 409), closing the cap TOCTOU. `WELCOME10`/`FREESHIP` are evergreen; `SAVE20` caps at 500. Seed coupons are CREATE-ONLY on reseed (`update: {}`) — reseeding never resets redemption bookkeeping.
- **`AUTH_SECRET` is enforced in production**: `assertAuthSecret` (`src/lib/auth-secret.ts`) throws at module load when `NODE_ENV=production` and the secret is missing or equals the dev constant. The build copies `.env` into `standalone/` — env changes need a rebuild.
- **Idempotency keys survive non-secure origins**: the checkout client mints keys via `newRequestId()` (`src/lib/random-id.ts`, session-7 S7-10) — `crypto.randomUUID` is secure-context-only and a plain-HTTP deploy used to crash checkout at mount. Keep the fallback.
- **Rate limiting**: in-memory fixed-window limiter (`src/lib/rate-limit.ts`) guards login/register/reviews/contact/newsletter/coupon/checkout/tracking/cart-POST-PATCH-DELETE-BULK/cart-summary-GET/wishlist-POST/search-GET/addresses-POST-PATCH-DELETE. Keys are per-email **plus per-IP** for credentials (`login-ip:`/`register-ip:` budgets — rotating emails must not mint fresh budgets), per-IP elsewhere; the shared `clientIp(Headers)` helper is spoof-resistant (session-6): `cf-connecting-ip` wins, else the RIGHTMOST `x-forwarded-for` hop (the value the nearest trusted proxy appended — never the leftmost, which the client controls), else the shared `direct` bucket. Every limiter call site keys through this helper — the five historical inline `split(",")[0]` copies are gone. Limits are generous (humans and e2e pass; search and cart-summary are 120/min, writes 60/min, cart-bulk 10/min). Swap internals for a shared store if you scale out.
- **Stock is reserved atomically**: checkout decrements via conditional `updateMany({ where: { id, stock: { gte: qty } } })` and rolls back on `count === 0` — never reintroduce check-then-decrement.
- **Zero-quantity cart lines cannot exist**: the cart PATCH deletes a line whose clamped quantity is 0 (`clampPurchaseQuantity`); checkout 409s on `quantity <= 0` lines as a backstop. The cart **POST** runs read+upsert inside one `$transaction` and routes through the SAME clamp (stock ceiling + 99 cap) — POST and PATCH can never disagree; concurrent add-to-carts never lose an increment. Every PATCH write is a scoped conditional write (`{ id, cartId }`) whose `count === 0` maps to the same 404 (session-10 S10-2) — a line deleted by a concurrent tab surfaces as "not found", never as a P2025 500.
- **Product images are root-relative ONLY** (session-7 S7-6): `imageUrlSchema` (`src/lib/validation.ts`) accepts `/…` store paths and nothing else — the previous http(s) branch passed validation but the `img-src 'self' data:` CSP silently blocked the render. External hosts require a deliberate CSP-widening decision, not a schema edit. Pinned in `tests/unit/validation.test.ts`.
- **Admin money inputs are bounded**: price/compareAtPrice carry `.max(100_000_000)` (session-7 S7-7) — a typo can no longer surface as an opaque Int32 Prisma error.
- **Wishlist heart labels carry the product name** (session-7 S7-13) and every product grid heart reads the wishlist state.
- **Review aggregates grow, never collapse** — and the growth is TRANSACTIONAL (session-8 S8-2): `submitReviewAction` runs read→`mergeReviewAggregate`→write inside ONE `db.$transaction` via `growReviewAggregate` (`src/lib/review-aggregate.ts`) — two concurrent submissions can no longer lose an increment (the read-modify-write used to straddle transactions). Do NOT replace with a from-scratch row-count recompute: the seed ships reference-parity display counts with one template row, and a recompute collapses 412 → 2 on the first real review. The seed itself is also content-only now (session-7 S7-3) — a reseed can never collapse them either.
- **The admin dashboard aggregates in SQL** (session-9 S9-4): the 14-day revenue chart folds `SUM(total) GROUP BY date(placedAt/1000,'unixepoch')` day buckets via pure `buildRevenueChart` (`src/lib/analytics.ts`, unit-pinned) — never re-introduce the unbounded `order.findMany` JS fold. Prisma stores SQLite DateTimes as epoch-millis INTEGERs, so the bare `date(placedAt)` form returns NULL; the `/1000,'unixepoch'` form is required. Schema hot-path indexes: `Address.userId`, `Session.expiresAt` (S9-5), plus the pre-existing catalog/order indexes.
- **SEO surfaces stay private**: `sitemap.ts` lists only public catalog/content routes (no login/register/cart/wishlist/track-order/checkout/account/admin); `robots.ts` disallows `/admin`, `/account`, `/checkout`, `/api`; and every private surface ships `<meta name="robots" content="noindex…">` — wishlist/checkout/success/admin/not-found (session-5/6), plus cart/track-order/account/checkout/login/register (session-8 S8-9; query-permutation deep links like `/track-order?number=…&email=…` stay out of the index). Pinned by `tests/unit/seo-routes.test.ts` + the seo-platform e2e. Never "helpfully" add private routes back.
- **JSON-LD is builder-owned**: all schema.org structured data comes from the pure builders in `src/lib/seo.ts` (`buildProductJsonLd`/`buildOrganizationJsonLd`/`buildWebsiteJsonLd`, unit-pinned in `tests/unit/seo-ld.test.ts`) — the Product block (with `priceValidUntil`) on product pages, Organization + WebSite (with the `/products?q=` SearchAction) on every storefront page. Never hand-inline JSON-LD in a page. Cents → dollars conversion lives there (`Math.round(cents)/100`); `ld+json` data blocks are NOT subject to `script-src` nonces.
- **Canonicals + share cards are site-wide**: every public page emits `alternates.canonical` from `siteBaseUrl()` (session-6 S6-4; `/products` canonicalizes its facet permutations to the un-parameterized URL), and every page inherits the OpenGraph/Twitter share cards (`public/images/og-default.png` + `summary_large_image`); product pages swap in their first product image. Pinned by `tests/e2e/seo-platform.spec.ts`.
- **The seed refreshes catalog content, never live data** (session-7 S7-3, `src/lib/seed-policy.ts`): product upserts refresh name/copy/category/images/tags/specs ONLY — price, compareAtPrice, stock, rating, reviewCount, sku, badge, featured/newArrival, isActive are admin- or traffic-owned; settings + carousel slides are create-only (coupon precedent, S4-8). Unit-pinned in `tests/unit/session7-hardening.test.ts`; live-verified in session 7. If you add a product field, decide explicitly which side of the line it belongs on.
- **The address book is bounded and single-defaulted on EVERY write path** (session-7 S7-8 + session-8 S8-1 + session-10 S10-1/S10-3): `MAX_ADDRESSES_PER_USER = 20` (`src/lib/addresses.ts`) gates `/api/addresses` POST (friendly 409 — the cap check runs INSIDE the create transaction since S10-3, so concurrent POSTs at cap − 1 cannot overshoot) and checkout `saveAddress` (skip-save, order still places); the account POST runs cap+count+create inside ONE `$transaction` and the FIRST saved address becomes `isDefault: true` (so checkout prefill actually fires — the "check out in seconds" copy is now true); `PATCH /api/addresses` (`addressDefaultSchema`) promotes an address and unsets the previous default in the same transaction; a default-making checkout save does the same; DELETE of the default re-promotes the newest remaining row (S10-1). `findFirst({ isDefault: true })` is deterministic everywhere. E2e-pinned (addresses-cap + addresses-default specs); unit-pinned (`assertAddressCap` + `reassignDefaultAfterDeleteInTx`).
- **The wishlist is bounded and "Add All" is ONE request** (session-8 S8-6 + session-10 S10-4): `MAX_WISHLIST_ITEMS = 100` (`src/lib/wishlist.ts`) gates `/api/wishlist` POST with a friendly 409, and the guest→user login merge plans its upserts through `planWishlistMerge` (cap-truncating, dedupe, already-owned skip) so a merge can NEVER push the user over the cap — the merge is the second create path, and the old unbounded loop left overflow permanently invisible behind the page's `take: MAX_WISHLIST_ITEMS`; the wishlist page reads with `take: MAX_WISHLIST_ITEMS`; `POST /api/cart/bulk` (`cartBulkSchema`, limiter 10/min) applies the SAME per-line clamp/upsert as the single POST inside ONE transaction — the sequential add-all loop used to fight the shared 60/min cart limiter on large wishlists — and reports BOTH skip reasons (gone/inactive AND sold-out-under-the-click, S10-5) in `skipped` so the "added N of M" toast arithmetic always adds up. Wishlist toggles delete via `deleteMany` (session-8 S8-4 — a concurrent toggle must not surface a P2025 500 for a click that succeeded).
- **P2002 target matching is tolerant of both engine shapes** (session-8 S8-3): `isUniqueViolation`/`uniqueTargetField` (`src/lib/prisma-errors.ts`) match field-array targets (`["idempotencyKey"]`, `["Order.idempotencyKey"]`), bare strings, AND constraint-NAME strings (`"Order_idempotencyKey_key"`) — the checkout retry loop branches on `uniqueTargetField(error, "idempotencyKey")`; matching only the field shape would silently disable the S7-2 recovery branch whenever the engine reports the name form. Route handlers import from the module; no private copies.
- **JSON-LD is serialized through `jsonLdScript()`**: all three `ld+json` blocks (product page + storefront layout) escape `<`/U+2028/U+2029 (`src/lib/seo.ts`, session-7 S7-9) so admin-authored strings cannot terminate the element early. No bare `JSON.stringify` into `dangerouslySetInnerHTML`.
- **The base URL is single-sourced**: `siteBaseUrl()` (`src/lib/seo.ts`) is the ONLY place the `NEXT_PUBLIC_SITE_URL || "http://localhost:3000"` fallback exists — metadataBase, sitemap, robots, canonicals and JSON-LD all compose from it (session-7 S7-4 completed the sweep).
- **The guest→user cart merge is planned, then applied atomically**: `computeMergedQuantities` (`src/lib/cart-merge.ts`, unit-pinned) produces the final per-product quantities (sums, 99 ceiling, zero-sum lines dropped, and — since session-6 S6-6 — clamped to live product stock when the caller passes the stock map, which `cart.ts` always does). The merge + guest-cart delete + token rotation run inside ONE `db.$transaction` with idempotent `update: { quantity }` writes (a retried merge cannot double-count); the wishlist merge mirrors the same transactional pattern (`src/lib/wishlist.ts`). Cart/wishlist creates catch the token `@unique` P2002 race and re-read the winner. Never reintroduce the increment-loop or a non-transactional merge.
- **The receipt copy never promises email**: nothing in the codebase sends email — the checkout-success copy points at the token-gated receipt link and Track Order instead. Pinned by the shopping-flow e2e (`on its way` must never reappear). A real mailer is an epic (provider credentials + bounce handling), not a copy fix.
- **Error boundaries are branded**: `(storefront)/error.tsx` + `global-error.tsx` render the store's error card (reset + back-to-products), not Next's default screen. Keep them dependency-free.
- **Platform hygiene**: `poweredByHeader: false`, HSTS with `includeSubDomains`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()` (`next.config.ts`); `src/app/icon.svg` + `src/app/manifest.ts` ship the favicon/manifest — pinned by `tests/e2e/seo-platform.spec.ts`. No `bun.lock` is committed (npm is the package manager).
- **Uniform auth errors**: login failures return exactly "Invalid email or password." (with a dummy scrypt burn for unknown accounts) — do not "helpfully" distinguish unknown-email from wrong-password.

## Process discipline

- Git: `main` only, Conventional Commits, atomic commits, never commit secrets (`.gitignore` rejects `.env`, `*.key`, `ssh-key.txt`, `db/*.db`).
- Pushes use `docs/ssh_git_wrapper_v3.py` — see `docs/how-to-git-push-using-ssh-wrapper_SKILL.md`. The verification gate above is the only gate; it must be green first.
- `homenest-store-s_SKILL.md` is the full engineering reference (20 sections + trap logs + playbooks); `docs/REMEDIATION_PLAN.md` records the session-2/3/4 security audits and their fixes; `scripts/capture-screenshots.mjs` regenerates `docs/screenshots/`.
- E2E ordering: `npm run build` before `npm run test:e2e` (the suite starts the standalone server). Tests wait for hydration via `gotoHydrated()` (`tests/e2e/helpers.ts`) — keep using it for any new spec; clicks before hydration fall back to native form GET. Playwright quirk: `request.post(url, { data: "<string>" })` JSON-encodes the string — send `Buffer` data for genuinely malformed-JSON tests.
- When a test fails, reproduce against the standalone server before touching code — the suite caught three real production bugs (Toaster nesting, CSP nonce hydration, toast/action races) exactly this way.
